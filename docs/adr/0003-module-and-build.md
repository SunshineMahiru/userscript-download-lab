# ADR-0003 源码模块化与打包方式

- 状态：已采纳
- 日期：2026-11-09
- 影响范围：目录结构、构建流程、全部测试

## 背景

现有实现是单个文件，1098 行。测试要访问内部函数，必须把整份脚本放进 `vm` 里求值，再挂上全局的请求与下载接口。这种方式随代码增长会越来越难维护：任何一次重构都可能让求值的上下文失效，而失败信息只指向求值那一行。

项目规则原先要求「交付物是单个 `.user.js`，不引入打包工具」。新版规则删掉了这一条，选择空间重新打开。

用户脚本生态里，模块化的通行做法是「源码分模块 + 打包成单文件」：`vite-plugin-monkey` 2070 星，`webpack-userscript-template` 155 星，`rollup-userscript-template` 50 星，方向一致。

## 决策

源码按职责分到 `src/` 下的 ES 模块，测试直接 `import` 被测函数。

用 `esbuild` 打包成单个 `.user.js`，产物放在 `dist/`，不纳入版本库。

只引入一个开发依赖。构建脚本控制在 40 行以内，只做三件事：注入元数据块、打包、校验产物的首尾标记。

## 后果

正面：

- 测试不必再求值整份脚本，失败信息指向具体的模块与行。
- 模块边界等于文件边界，按文件名就能建立结构印象，不需要靠注释约定。
- 产物仍是单个文件，安装方式与之前完全一样。
- 打包器能顺带发现未使用的导出与拼写错误。

负面：

- 新增构建步骤，跑测试前必须先构建，否则端到端测试拿到的是旧产物。
- 产物与源码行号对不上，线上报错要回到源码里二次定位。项目不引入 sourcemap，因为脚本管理器对 sourcemap 的支持不一致。
- 构建脚本本身成为需要维护的代码，它与 `src/` 的目录结构耦合，新增模块时要同步。
- `dist/` 不跟踪意味着使用者要先装依赖再构建，使用门槛高于直接下载。

## 被否选项

**维持单文件，内部用分节注释维持边界。** 好处是零构建、下载即用。否掉的理由是测试必须继续用 `vm` 求值整份脚本，而随着函数增多，求值上下文与真实运行环境的差异会越来越难排查。

**源码分片但不打包，构建脚本按固定顺序拼接。** 好处是既有模块文件又不引依赖。否掉的理由是片段不是合法 ES 模块，编辑器的跳转、重命名、未使用变量检查全部失效；顺序写错只在运行时暴露，报错行号还与源码错位。它同时承担了前两种做法的缺点。
