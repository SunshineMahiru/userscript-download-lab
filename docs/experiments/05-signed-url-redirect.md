# 实验五：签名地址与 302 跳转

## 问题

资源地址通常不是最终地址。第一段返回 302，跳到带签名与过期时间的真实地址；签名过期后返回 403。这条链路对下载器有两个要求：要跟随重定向，要把 403 与本地的其他失败区分开。

如果下载器把 302 当成失败，或者在签名过期时只报「下载失败」，用户无从判断是资源下架还是链接过期。

## 方法

合成站点按真实形态分两段：

1. `/media/<文件>` 返回 302，`Location` 指向 `/media/blob/<文件>?exp=<时间戳>&token=<签名>`。
2. `/media/blob/<文件>` 校验签名与时间：签名不匹配返回 `invalid signature`，时间已过返回 `signature expired`，都带 403。

签名算法为 `sha256(文件名:过期时间:固定串)` 取前 32 位十六进制。固定串只用于让签名在多次请求之间保持一致，没有安全含义。

## 复跑命令

```bash
node tests/server.test.mjs
node tests/engine.test.mjs
```

## 数据

第一段响应的 `Location` 形状（正则直接断言）：

```
/media/blob/doc-1.pdf?exp=1794213778913&token=<32 位十六进制>
```

第二段的三种结果：

| 条件 | 状态 | 响应体 |
| --- | --- | --- |
| 签名正确且未过期 | 200 | `application/pdf`，正文以 `%PDF-1.4` 开头 |
| 签名被篡改 | 403 | `{"error":"invalid signature"}` |
| 签名正确但已过期 | 403 | `{"error":"signature expired"}` |

引擎层的表现：五条资源中四条下载成功，过期那条记录为 `http-403`，其余三条正常完成，整批不中断。

## 结论

两种情况都返回 403，但错误体不同。测试分开断言，是为了证明服务端能区分，而不是笼统断言「403 就是过期」。

引擎在批处理里对单条失败的处理是记录而非中断。这个选择有代价：用户可能看到「4 成功 1 失败」，而不是一次干脆的失败。但整批中止会让一条过期资源挡住其余全部资源，代价更大。

对 302 的处理沿用传输层默认行为（跟随跳转）。这意味着签名地址不会暴露给上层，上层拿到的始终是最终响应。副作用是排错时看不到中间跳转，只能在传输层的日志里查。

## 局限

合成站点的签名不使用真实的时间窗口（过期时间由固定差值给出），不模拟「下载到一半过期」。真实环境下大文件下载跨越签名有效期会得到半截文件，本实验没有覆盖。

跳转只测了一层。真实场景可能出现两跳以上，或者跳到另一个域名，后者还涉及脚本管理器的域名放行。合成站点不模拟跨域名跳转。
