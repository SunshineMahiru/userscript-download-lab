# 实验三：文件名的三处边界

## 问题

下载文件名来自站点返回的标题，可能是中文、可能带冒号与问号、可能超过系统限制。脚本管理器把文件名直接交给浏览器下载器，浏览器再交给文件系统。任何一环不接受，下载就会失败或得到被截断的名字。

需要确认三处边界：Windows 保留名、结尾的点与空格、UTF-8 字节上限。

## 方法

按顺序处理：

1. 替换 Windows 非法字符 `<>:"/\|?*` 与控制字符为下划线。
2. 后缀以真实地址为准：站点标题写 `.pptx`、实际地址是 `.pdf` 时，取地址的后缀。
3. 去掉结尾的点与空格。
4. 按 UTF-8 字节截断主体，上限 168 字节，为后缀与分隔符留出余量。
5. 命中 Windows 保留名时前置下划线。

## 复跑命令

```bash
node tests/filename.test.mjs
```

## 数据

| 输入 | 输出 | 触发的规则 |
| --- | --- | --- |
| `第3章 绪论.pptx` + 地址 `.pdf` | `第3章 绪论.pdf` | 后缀跟随地址 |
| `讲义.zip` + 无后缀地址 | `讲义.zip` | 保留原名后缀 |
| `讲义.pptx` + 地址 `1.png` | `讲义.pptx` | png 不当作文件后缀 |
| `CON` | `_CON` | 保留名 |
| `null` | `_null` | 保留名 |
| `报告.` | `报告` | 去掉结尾点 |
| `a:b*c?.pdf` | `a_b_c_.pdf` | 非法字符替换 |
| 200 个汉字 + `.pdf` | 172 字节以内，后缀完整 | 字节截断 |

字节截断这一条：200 个汉字是 600 字节，直接按字符截断会切在半个汉字上，产生乱码。按字节累积、遇到超限立即停止，保证切点位于完整字符边界。

## 结论

三处边界里最容易漏的是**保留名**。`CON`、`NUL`、`COM1` 这些在 Windows 上是设备名，同名文件无法创建，且失败信息通常只有「无法保存」四个字，排查成本高。

其次容易漏的是**结尾的点**。浏览器会把 `报告..pdf` 交给系统，Windows 在保存时静默去掉结尾的点，得到 `报告.pdf`；而 Linux 上会保留，同一份代码在两个平台产出不同文件名。

字节上限取 168 而不是 255，是为后缀（最长约 5 字节）与可能的重名后缀（` (1)` 等，约 4 字节）留出空间。取满 255 会在追加后缀时溢出。

## 局限

不同文件系统的上限不同：ext4 是 255 字节，NTFS 是 255 个 UTF-16 码元，两者对中文的计数方式不一样。本实现按 UTF-8 字节保守处理，在 ext4 上安全，在 NTFS 上会略早截断。

macOS 的 HFS+ 用 UTF-16 分解形式存储，某些合成字符会被重新组合，文件名可能与预期差一个码位。这一点没有条件实测。
