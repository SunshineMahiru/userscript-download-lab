# 实验六：游标分页的取全策略

## 问题

列表接口分页，第一页返回一个游标，传回去取下一页，游标为空表示到底。取全需要循环，而循环有三个容易写错的地方：

- 适配器声明不支持分页，代码却仍去取第二页。
- 服务端返回空游标，代码把它当成有效值继续请求，形成重复请求。
- 请求次数与结果条数脱钩，测试只验条数不验次数，「多取了一页」这种错误查不出来。

## 方法

把分页写成显式循环，三个退出条件各自独立：

1. `listingRequest` 返回空值 —— 适配器认为没有下一页可拼。
2. 适配器 `capabilities.paging` 为 false —— 即使返回了游标也不用。
3. 返回的 `nextCursor` 为空 —— 服务端说到底了。

循环体只做三件事：拼请求、发请求、累积引用。

## 复跑命令

```bash
node tests/engine.test.mjs
node tests/server.test.mjs
```

## 数据

合成站点的两页数据：

| 页 | 游标 | 条数 | 返回的 `nextCursor` |
| --- | --- | --- | --- |
| 第一页 | `0` | 2 | `"1"` |
| 第二页 | `1` | 3 | `null` |

引擎取全的结果：

```
引用总数        5
请求次数        2
```

请求次数由传输层的日志统计，不是推测值。

越界处理：传入不存在的游标返回 404，引擎侧表现为传输类错误，不会静默返回空列表。

## 结论

把「请求次数」也断言进来，是本实验最有价值的一条。只断条数的话，多请求一次空页不会暴露——结果依然正确，只是白白多发一次请求。真实站点的分页接口常有速率限制，多余请求会累积成封禁风险。

三个退出条件分开写而不是合并成一个布尔判断，是因为它们的语义不同：`listingRequest` 返回空表示「这个适配器不支持多页」，`nextCursor` 为空表示「服务端说没有下一页」。合并后，在调试时无法区分是配置问题还是数据到底了。

## 局限

只测了两页。真实场景可能有几十页，循环中途某页失败时的行为本实现是向上抛出、整批放弃——没有做「跳过失败页继续」的容错。这个选择让结果要么完整要么报错，不会给出一个悄悄少了几条的列表。

游标的形式只测了递增数字串。真实接口可能用不透明字符串、时间戳或复合键，本实现对游标只做透传，不解析，因此形式不影响逻辑，但也没有针对这类形式的数据。
